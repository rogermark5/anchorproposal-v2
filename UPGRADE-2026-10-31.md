# Ubuntu upgrade: application dates, time zones and request recovery

These changes require the additive migrations `20261031010000_reliable_answer_requests` and `20261031020000_profile_ownership`. They add answer-request tracking, profile ownership and explicit Master profile grants. Existing applications, profiles, documents and conversations are preserved. Do not run `migrate reset`, `db push --force-reset`, or the seed script during this upgrade.

Admins can use profiles they create and additional profiles Master assigns. Existing profiles have no recorded owner: after this upgrade, Master must open Users, choose an admin's **Assign profiles** action, and assign the existing profiles that admin should use. Previous admin default selections do not grant access. Bidder assignments retain their existing behavior. Removing a Master assignment revokes additional profile access, including direct profile/application/document links; it does not delete data or remove the admin's own profiles.

## 6. Verify the domain and proxy

```bash
curl -I http://127.0.0.1:3100/login
curl -I https://anchorproposal.giize.com/login
curl --connect-timeout 3 --max-time 10 -i http://127.0.0.1:3001/auth/me
curl --connect-timeout 5 --max-time 15 -i https://anchorproposal.giize.com/backend/auth/me
pm2 logs anchor-api --lines 40 --nostream
pm2 logs anchor-web --lines 30 --nostream
tail -n 30 "$HOME/.pm2/pm2.log"
```

An unauthenticated `/auth/me` returning **401 with JSON** is expected, both directly and through the public `/backend` proxy. PM2 may show `online` before the API finishes starting. If the port refuses connections, inspect the current startup output and wait for the `API running on http://127.0.0.1:3001` message. If it remains unavailable, investigate the current logs before another restart. A login page returning 200 alone does not verify authenticated operations or prove that restarts have stopped. Watch PM2 uptime, restart count and memory during several complete import cycles and concurrent generations.

Once both services respond and a real sign-in succeeds, save the healthy process list:

```bash
pm2 save
```

If nginx handles the domain, inspect the existing TLS server block. The API route must preserve authorization headers and reach the API correctly. A typical direct API location is:

```nginx
location /backend/ {
    proxy_pass http://127.0.0.1:3001/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;
    proxy_buffering off;
}
```

Adapt the existing location, including any upload limits you already configured; do not replace your whole nginx/TLS configuration. The trailing slash on `proxy_pass` strips `/backend/`. Run `sudo nginx -t` successfully before `sudo systemctl reload nginx`. If you use another proxy, apply its corresponding timeout and streaming settings. This repository cannot change the Ubuntu proxy remotely.

The shared clients now retain login credentials during temporary server failures, coordinate token refresh, retry safe reads and keyed submissions, and show useful HTTP errors with request references. Answer generation uses short submission/polling requests while the work runs in Redis/BullMQ. Arbitrary write requests are not automatically repeated. A machine restart, unavailable database, proxy failure or disconnected internet still needs its underlying cause resolved.
